# P01 detailed work packages

These cards define implementation work; none is marked complete by this documentation revision. Current state and actual evidence live in [the canonical register](../delivery-register.yaml). [Gate criteria](../gates.md) own pass/fail outcomes; [status rules](../status-model.md) own state transitions. Estimates are focused person-days per package, excluding approval/access lead time and parallel effort. They are planning inputs to refine in P00.06, not elapsed commitments. Output paths identify artifacts to create or refine. Existing documents are inputs to review; code, accepted decisions and measured evidence must still be delivered through the package.

## P01.01 — Independent repository scaffolding

**Accountable role:** Engineering lead. **Contributors:** Console and all service owners.

**Prerequisites:** G00 core baseline; ADR-003/004/005/019 accepted; agreed contract ownership.

**Traceability:** R01 R02. Decisions: ADR-003 ADR-004 ADR-005 ADR-019. Acceptance criterion: **G01.01**.

**Estimate and confidence:** 5–8 person-days; medium confidence after spike.

Create seven independently buildable application boundaries and selected worker packages, each with owned locks, tests and image/build manifest. Use the documented Laravel/Python split and explicit migration ownership. Add only the minimal service/console health entrypoints required to prove the foundation; do not label scaffolds as completed domain services.

**Outputs:** Planned `apps/console/`, `services/{governance,catalogue,inventory,planning,lifecycle,assurance}/`, `workers/`, service lockfiles and container manifests; update corresponding existing service specifications.

**Acceptance checks:**

- Clean checkout builds all seven application images and selected workers from locks.
- A service-only change builds/deploys that service independently.
- No runtime import, shared private database model or bootstrap depends on legacy implementation.

**Required evidence:** Source revisions, dependency/image identities and actual build/typecheck/test output (E1). Store immutable references in the register; review procedure and evidence bindings: `docs/qualification/gate-reviews/g01.md`.

**Reviewer:** Engineering lead and owning service reviewer.

**Dependency/blocker treatment:** Input needed: approved runtime locks and build registry. Unblock: close ADR-003/005 dependencies; isolated library/domain work can continue. Create a register blocker only when confirmed; include scope, owner, unblock condition and next action.

## P01.02 — Local and integration runtime

**Accountable role:** SRE lead. **Contributors:** Security, developer experience and service owners.

**Prerequisites:** P01.01 buildable images; ADR-011/020 baseline accepted; dependency contracts from P01.05.

**Traceability:** R02. Decisions: ADR-005 ADR-011 ADR-020. Acceptance criterion: **G01.02**.

**Estimate and confidence:** 5–8 person-days; medium confidence.

Provide a local Compose runtime and isolated Kubernetes integration deployment with synthetic fixtures, approved network flows and deterministic configuration. Document exact installation order and dependency health. Separate environment configuration/secrets from image contents and use restricted endpoints; installation starts without native platform administrator authority.

**Outputs:** Planned `deploy/local/`, `deploy/integration/`, synthetic fixture declarations and `docs/operations/runbooks/install.md`; update `docs/operations/deployment-model.md`.

**Acceptance checks:**

- Install from an empty environment using documented prerequisites and pinned artifacts.
- Authenticated health checks pass; absent/misconfigured dependencies make readiness fail clearly.
- No production credentials/endpoints are required; network scope and synthetic identity are independently checked.

**Required evidence:** Installed inventory, configuration references and clean-install/health/negative results (E2). Store immutable references in the register; review procedure and evidence bindings: `docs/qualification/gate-reviews/g01.md`.

**Reviewer:** SRE lead and security reviewer.

**Dependency/blocker treatment:** Input needed: isolated runtime and DNS/PKI/registry access. Unblock: obtain integration prerequisites; local work is not proof of Kubernetes installation. Create a register blocker only when confirmed; include scope, owner, unblock condition and next action.

## P01.03 — Contracts and messaging foundation

**Accountable role:** Architecture lead. **Contributors:** PHP/Python service owners; quality and SRE.

**Prerequisites:** P00 ownership and ADR-008/012 decisions; P01.05 broker/PostgreSQL available for integration checks.

**Traceability:** R02 R15 R35. Decisions: ADR-004 ADR-008 ADR-012. Acceptance criterion: **G01.03**.

**Estimate and confidence:** 6–10 person-days; medium confidence.

Author versioned OpenAPI/AsyncAPI/schema contracts from the reviewed examples. Build generated-client and PHP/Python conformance checks, error/idempotency conventions, and minimal transactional outbox/inbox reference implementation inside each owning service. Prove delivery semantics against real local dependencies; an event cannot grant authority or silently execute native effects.

**Outputs:** Planned `contracts/openapi/`, `contracts/asyncapi/`, `contracts/schemas/`, `tests/contracts/` and messaging foundation in owning services; update `docs/contracts/README.md` and examples.

**Acceptance checks:**

- Same valid/invalid fixtures produce compatible PHP/Python interpretation, including tenant/actor/revision/digest fields.
- Unsupported payload/version and wrong-tenant/caller fixtures fail deterministically.
- Injected outbox persistence failure rolls back the associated write; duplicate delivery creates one logical consumer effect and restart resumes dispatch.

**Required evidence:** Schema/client revisions and cross-language, negative, transaction and restart reports (E1/E2). Store immutable references in the register; review procedure and evidence bindings: `docs/qualification/gate-reviews/g01.md`.

**Reviewer:** Architecture and independent quality reviewers.

**Dependency/blocker treatment:** Input needed: transport and compatibility rules. Unblock: resolve ADR-008/012; do not implement proprietary service-to-service payloads meanwhile. Create a register blocker only when confirmed; include scope, owner, unblock condition and next action.

## P01.04 — CI and artifact trust

**Accountable role:** Platform/SRE lead. **Contributors:** Security and service owners.

**Prerequisites:** P01.01 images/locks; ADR-010 trust and ADR-020 mirror/promotion constraints.

**Traceability:** R02 R31 R35. Decisions: ADR-003 ADR-010 ADR-012 ADR-020. Acceptance criterion: **G01.04**.

**Estimate and confidence:** 5–8 person-days; medium confidence.

Create per-service build/lint/typecheck/test and contract-compatibility jobs; add secret/dependency/image checks. Produce SBOMs, signed immutable images and a release manifest connecting source, locks and digests. Build once and promote verified artifacts; prove rejection of unsigned or mismatched artifacts.

**Outputs:** Planned `.github/workflows/`, artifact/signing policy and `release/` manifests; `docs/operations/runbooks/promote-release.md`.

**Acceptance checks:**

- A coherent service change triggers its checks and required dependent contract checks.
- Manifest/SBOM/signature resolve to the same image digest and source revision.
- A deliberately unsigned or altered artifact fails promotion; logs contain no exposed secrets.

**Required evidence:** CI runs, provenance/digests, signature verification and negative promotion evidence (E1/E2). Store immutable references in the register; review procedure and evidence bindings: `docs/qualification/gate-reviews/g01.md`.

**Reviewer:** Security and SRE reviewers independent of the change author where required.

**Dependency/blocker treatment:** Input needed: supported signer/registry/mirrors. Unblock: establish approved trust dependencies; unsigned local builds remain development artifacts. Create a register blocker only when confirmed; include scope, owner, unblock condition and next action.

## P01.05 — Stateful dependencies and identities

**Accountable role:** SRE lead. **Contributors:** Security, lifecycle and service database owners.

**Prerequisites:** ADR-006/007/008/009/010/011 initial selections; integration environment available.

**Traceability:** R02 R29. Decisions: ADR-006 ADR-007 ADR-008 ADR-009 ADR-010 ADR-011. Acceptance criterion: **G01.05**.

**Estimate and confidence:** 6–10 person-days; low confidence until platform interfaces are known.

Deploy pinned PostgreSQL, Temporal, broker, protected object storage and selected cache/session dependencies. Create separate context databases, restricted runtime roles and controlled migrator identities. Integrate approved secrets/PKI and workload identities; document ownership, health, durable storage and restore dependencies.

**Outputs:** Planned `deploy/dependencies/`, per-service migrations/role definitions and `docs/operations/runbooks/dependency-recovery.md`; update deployment model with exact accepted versions.

**Acceptance checks:**

- Runtime identities cannot read another context database or perform schema administration.
- Controlled migrations run through the correct identity and are attributable to an artifact revision.
- Invalid/revoked identity, missing secret/key and dependency unavailability yield defined denial/readiness behavior without fallback administrator credentials.

**Required evidence:** Deployed version inventory, role/identity negative tests and controlled migration results (E2). Store immutable references in the register; review procedure and evidence bindings: `docs/qualification/gate-reviews/g01.md`.

**Reviewer:** Security and owning service/database reviewers.

**Dependency/blocker treatment:** Input needed: approved secret/identity services and durable storage. Unblock: complete initial ADR decisions; temporary mocks cannot satisfy G01.05. Create a register blocker only when confirmed; include scope, owner, unblock condition and next action.

## P01.06 — Baseline operations and recovery

**Accountable role:** SRE and security leads. **Contributors:** Quality and receiving operations representatives.

**Prerequisites:** P01.02/P01.04/P01.05 runnable foundation; P00.05 initial targets.

**Traceability:** R29 R30 R31. Decisions: ADR-009 ADR-010 ADR-011 ADR-017 ADR-020. Acceptance criterion: **G01.06**.

**Estimate and confidence:** 6–10 person-days; medium confidence.

Implement health, correlated logs/traces/metrics and actual alert delivery; enforce initial deny-by-default network/identity policy. Restore synthetic database and evidence objects and check their identity/digests. Rehearse failed deployment recovery and safe restart with native writes disabled. Record baseline resource cost and installation/recovery steps for another operator.

**Outputs:** Planned `deploy/observability/`, `tests/integration/`, `tests/recovery/` and `docs/operations/runbooks/{restore-control-plane,handle-alert,rollback-deployment}.md`.

**Acceptance checks:**

- Restore both database records and evidence objects; independently compare expected identities/digests.
- Restart preserves durable foundation records and never enables native operations by default.
- A test alert reaches the receiving route and is acknowledged; redaction and correlation are inspected.
- Failed deployment/recovery follows the runbook with recorded elapsed time and limitations; do not claim the full P10 recovery objective yet.

**Required evidence:** Restore/restart/deploy recovery reports, alert receipt and operational review (E2). Store immutable references in the register; review procedure and evidence bindings: `docs/qualification/gate-reviews/g01.md`.

**Reviewer:** Independent SRE/qualification reviewer and receiving operations representative.

**Dependency/blocker treatment:** Input needed: approved backup storage, alert receiver and recovery environment. Unblock: obtain these specific dependencies; successful backup creation alone is insufficient. Create a register blocker only when confirmed; include scope, owner, unblock condition and next action.
