# P03 — Application catalogue and workspace

Deliver revisioned portable application intent and operator journeys without binding product identity to a platform VM.

**Accountable lead:** Product engineering lead. Individual assignees and reviewers are recorded when assigned.

**Entry:** G01 foundation and usable P02 tenant/authorization interfaces; ADR-013 invariants reviewed.

**Sequence:** P03.01 → P03.02/P03.03 → P03.04; P03.05 supplies continuous negative verification.

Use the [programme plan](../phased-plan.md), [canonical delivery register](../delivery-register.yaml), [requirements](../requirements-and-qualification.md) and [decision register](../../decisions/decision-register.md) together. The register owns current state and evidence; these cards define delivery scope. Refine staffing and estimates using the [estimation model](../estimation-and-dependencies.md) before starting each package.

## Work packages

### P03.01 — Core aggregates

**Owner:** Catalogue. **Traceability:** R05 R06; G03.01 G03.02.

**Dependencies and inputs:** P00.02/ADR-013 cardinalities, P02.02 tenancy and P01.03 schema conventions.

**Outputs:** Catalogue aggregate schemas, migrations, APIs and invariant fixtures for applications, workloads, environments, WSDs and domain associations.

1. Implement stable product identities separately from native resource references.
2. Enforce tenant ownership, reference lifetime and allowed associations at the authoritative writer before emitting revision events.

**Acceptance:** Valid multi-workload/multi-domain intent persists; cross-tenant links and impossible domain associations fail without partial writes.

**Evidence and review:** Record artifact/source identities, actual observations and failed cases at the levels specified by G03.01 G03.02. Reviewer: Catalogue owner and architecture lead.

### P03.02 — Intent semantics

**Owner:** Catalogue. **Traceability:** R05 R06 R07 R19; G03.01 G03.02.

**Dependencies and inputs:** P03.01 aggregates and reviewed domain model; application owner supplies dependency and service intent.

**Outputs:** Revisioned requirement/dependency schema with compute, disk, NIC, security, service and recovery dimensions.

1. Represent dependency direction, readiness conditions, disk/NIC order and requirement strength explicitly.
2. Validate graph cycles and references while retaining unsupported requirements for later explainable assessment.

**Acceptance:** Cyclic or dangling dependencies fail deterministically; a required unsupported control survives round-trip and is never silently dropped.

**Evidence and review:** Record artifact/source identities, actual observations and failed cases at the levels specified by G03.01 G03.02. Reviewer: Architecture and quality leads.

### P03.03 — Revision behavior

**Owner:** Catalogue. **Traceability:** R05; G03.03.

**Dependencies and inputs:** P03.01 authoritative aggregates; PostgreSQL/broker foundation from P01.03/P01.05.

**Outputs:** Immutable revision API, optimistic concurrency and tenant-scoped idempotency journal.

1. Commit aggregate revision, audit reference and outbox fact atomically.
2. Bind idempotency keys to tenant, action and payload; reject changed payload reuse and stale expected revisions.

**Acceptance:** Duplicate retry yields one revision; injected outbox failure rolls back; concurrent stale writer receives a deterministic conflict.

**Evidence and review:** Record artifact/source identities, actual observations and failed cases at the levels specified by G03.03. Reviewer: Independent quality reviewer.

### P03.04 — Product workflows

**Owner:** Console/catalogue. **Traceability:** R05 R33; G03.01 G03.04.

**Dependencies and inputs:** P03.01–P03.03 APIs and P02.05 console foundation; synthetic walkthrough dataset.

**Outputs:** Application create/edit/import, dependency view, revision comparison and validation-error journeys.

1. Use generated service clients and expose stable operation/revision identifiers to operators.
2. Design actionable errors, unsaved-change recovery and accessible revision comparison using real API outcomes.

**Acceptance:** An application owner completes the synthetic journey and explains differences; no console path reads a domain database directly.

**Evidence and review:** Record artifact/source identities, actual observations and failed cases at the levels specified by G03.01 G03.04. Reviewer: Product owner and representative operator.

### P03.05 — Domain verification

**Owner:** Quality. **Traceability:** R04 R05 R06; G03.02 G03.03 G03.04.

**Dependencies and inputs:** P03.01–P03.04 usable slice and Q01 campaign design; independent test fixtures.

**Outputs:** Domain/API/browser test matrix and evidence references for tenant, revision and persistence failures.

1. Exercise invalid ownership, dangling references, revocation, interrupted requests and replay against real dependencies.
2. Run representative-user journeys with keyboard access and stale concurrent edits; record actionable defects against owning packages.

**Acceptance:** Q01 covers every aggregate invariant and retry boundary; failures identify the violated rule and preserve prior intent.

**Evidence and review:** Record artifact/source identities, actual observations and failed cases at the levels specified by G03.02 G03.03 G03.04. Reviewer: Quality lead independent of feature author.

Update the owning service/contract, operating procedure and evidence references with the change. Keep actual gate decisions in the delivery register, regenerate progress/traceability, and update `next_work.md` with the next executable action.
