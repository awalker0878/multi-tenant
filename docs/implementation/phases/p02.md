# P02 — Identity, tenancy and governance

Establish identity, tenant scope and approval decisions that every service can enforce independently.

**Accountable lead:** Product engineering and IAM leads. Individual assignees and reviewers are recorded when assigned.

**Entry:** G01 foundation; implement the accepted [ADR-009](../../decisions/adr-009-identity-delegation-and-authorization.md) console-managed OIDC/local-bootstrap baseline and resolve its remaining identity contracts before affected packages. Production OIDC settings are entered through the console when configuring an installation, not supplied as deployment inputs or prerequisites for P02 development.

**Sequence:** P02.01 → P02.02/P02.03 → P02.04; P02.05 can develop against agreed contracts.

**Development entry:** the requesting user authorized continued P02 implementation
on 2026-10-05 in [the entry record](../p02-development-entry.md). P02.01/P02.05
start with [local bootstrap](../p02-local-bootstrap.md). G01 receiving conditions
remain open; development entry does not pass G01/G02 or authorize promotion.

Current tenant, authorization and approval behavior and limitations are recorded in
[the implementation increment](../p02-tenancy-and-approvals.md). The
[Console notification increment](../p02-console-notifications.md) adds a durable
product consumer and an owner-authorized, draft-preserving refresh journey.
The [accepted support policy and implementation](../p02-support-access.md) adds
bounded diagnostic access, separate tenant/security decisions, immutable audit and
independent post-use review. EV-P02-020–022 qualify it; actual custody/accessibility
and independent G02 receiving inputs remain in the [completion review](../p02-completion-review.md).

## Work packages

### P02.01 — Authentication

**Owner:** Product/IAM. **Traceability:** R03 R31; G02.01 G02.03.

**Dependencies and inputs:** P01.03 identity contracts and P01.05 workload identities; resolve ADR-009 issuer, audience and revocation semantics.

**Outputs:** Idempotent deployment bootstrap, local administrator/password-change lifecycle, Governance OIDC connection/authentication interfaces, console sessions and identity conformance fixtures.

1. Create one installation-local administrator through an authorized deployment operation, generate/display its random temporary password once and persist only its hash with mandatory-change state. Require a different password at first login before any protected function other than change/logout; enforce the restriction in direct APIs and rotate session authority after change.
2. Persist OIDC provider/client settings and claim mappings through console-driven Governance APIs; protect write-only secret input. No OIDC values come from environment variables, deployment manifests or static configuration files. Test federated administrative access before atomic activation and local-account/session retirement.
3. Bind federated identities to stable subjects and approved issuers; validate audience and expiry independently in each owning API.
4. Implement browser session creation, rotation, logout and CSRF controls; exercise service identity rotation without shared administrator fallback. Preserve setup/change/retirement state across replicas, retries, restart and restore.

**Acceptance:** Installation reaches local setup without OIDC deployment values. Temporary-password login cannot bypass mandatory change; the old password fails after change. Console-only OIDC configuration and a verified federated administrator complete handover, revoke local sessions and disable local login. Failed provider tests preserve local setup; restarts/retries cannot recreate it and provider outages after activation cannot restore it. Forged issuer, wrong audience, expired token, stolen tenant selector and revoked service identity fail; issuer loss follows the approved fail-closed boundary.

**Evidence and review:** Record artifact/source identities, actual observations and failed cases at the levels specified by G02.01 G02.03. Reviewer: IAM/security and SRE leads.

### P02.02 — Tenancy

**Owner:** Governance. **Traceability:** R03; G02.01 G02.04.

**Dependencies and inputs:** P02.01 actor identity and P00.02 tenant model; approved membership and quota ownership.

**Outputs:** Tenant, membership, delegated-grant and quota APIs owned by governance; immutable audit events.

1. Implement lifecycle and revocation rules for memberships and grants with explicit tenant/site/environment scope.
2. Separate quota entitlement from observed capacity and reservations; publish revisioned facts through the transactional outbox.

**Acceptance:** At least two tenants retain independent memberships, grants and audit history; guessed IDs cannot cross scope; revocation prevents new privileged admission.

**Evidence and review:** Record artifact/source identities, actual observations and failed cases at the levels specified by G02.01 G02.04. Reviewer: Governance owner and security reviewer.

### P02.03 — Authorization

**Owner:** Governance/security. **Traceability:** R03 R04 R32; G02.01 G02.03.

**Dependencies and inputs:** P02.02 grant semantics and service resource ownership; ADR-009 identity semantics and R32 sovereignty/access constraints.

**Outputs:** Permission matrix, owning-service authorization middleware and privileged support access policy.

1. Enumerate action, actor, delegated scope, resource and tenant checks for API, export, search, event and evidence paths.
2. Implement deny-by-default decisions and separation of duties; define explicit support-access approval and expiry instead of implied administrator reach.

**Acceptance:** Every denied matrix cell remains denied through direct APIs and projections; cached permissions cannot authorize a revoked grant at a privileged boundary.

**Evidence and review:** Record artifact/source identities, actual observations and failed cases at the levels specified by G02.01 G02.03. Reviewer: Security/IAM and owning service leads.

### P02.04 — Approval lifecycle

**Owner:** Governance. **Traceability:** R03; G02.02 G02.04.

**Dependencies and inputs:** P02.03 authority checks and the plan-binding interface agreed in P00/P01; P05.04 later implements its plan producer. P02 approval tests use bound synthetic plans.

**Outputs:** Approval state machine and API, revocation/expiry events and break-glass audit contract.

1. Bind approval to immutable digest, action, scope, actor constraints and validity window.
2. Implement request, approve, reject, revoke and expire transitions with immutable history and independent approver checks.

**Acceptance:** Changing a bound field cannot reuse approval; requestor self-approval is denied where separation applies; restart preserves decision history.

**Evidence and review:** Record artifact/source identities, actual observations and failed cases at the levels specified by G02.02 G02.04. Reviewer: Governance owner and quality lead.

### P02.05 — Console foundation

**Owner:** Console. **Traceability:** R03; G02.01 G02.04.

**Dependencies and inputs:** P02.01 sessions, P02.02 membership selection and ADR-019 browser delivery choice.

**Outputs:** Console first-login password change, external OIDC administration/test/activation, tenant/account navigation, access-denied journeys and shared accessible components.

1. Implement the local-login/password-change journey and Administration → Identity provider using Governance-owned setup state. Keep password and client-secret inputs out of page props, history, remembered state and subsequent responses. Explain failed connection tests and complete the verified OIDC handover before retiring local access.
2. Render only authorized tenant choices and explicit loading, expiry and denied states.
3. Implement keyboard focus and error handling for session loss or revoked membership; let owning APIs make every authority decision.

**Acceptance:** The administrator completes first-login password change and OIDC setup by keyboard; no configuration-file edit is needed. Invalid connection details retain safe setup access, secrets are never returned, and retired local sessions are denied. Representative delegated roles can select tenants and recover from expired sessions; manipulated browser state grants no extra API access.

**Evidence and review:** Record artifact/source identities, actual observations and failed cases at the levels specified by G02.01 G02.04. Reviewer: Product owner and independent quality reviewer.

## Engineering acceptance detail

Apply [security and tenancy](../../engineering/security-and-tenancy.md) and [frontend conventions](../../engineering/frontend.md) to each card. P02.01 tests real request-forgery middleware, login/session rotation, logout, trusted host/proxy boundaries and expired submissions. P02.02/P02.03 cover tenant scopes in binding, raw/bulk queries, caches, files, search, queues and exports; a global model scope or hidden button is insufficient. Recheck current authority for new commands and protected retrieval while preserving authorized processing of previously committed audit/evidence facts.

P02.05 tests tenant switches with late responses, multi-tab requests, shared/deferred/partial props, cleared history/remembered state and scoped validation errors. Run keyboard and representative assistive-technology checks against the selected WCAG 2.2 AA scope. Browser floor and build success are separate from qualified managed-browser support. Use the expanded Q01 matrix and link results to G02.01/G02.04.
