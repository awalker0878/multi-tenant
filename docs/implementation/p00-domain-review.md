# P00 domain and ownership review

Review performed: 2026-10-04. Work package: P00.02. Criterion: G00.02. Status: analytical review completed; accountable architecture, service and security review remains pending. This is an E0 design analysis, not runtime evidence, schema approval or a completed gate. No platform or service endpoint was contacted.

## Review scope and result

Reviewed the current [domain model](../product/domain-model.md), [Permit Desk walkthrough](../product/application-walkthrough.md), all seven [service specifications](../services/README.md), [contract conventions](../contracts/README.md), [exchange examples](../contracts/examples.md), [context registry](../../architecture/context-map.yaml) and ADRs [004](../decisions/adr-004-service-context-boundaries.md), [012](../decisions/adr-012-contracts-and-event-evolution.md), [013](../decisions/adr-013-product-aggregate-invariants.md) and [024](../decisions/adr-024-pragmatic-laravel-domain-convention.md). Traced each example from authenticated actor through the record owner to the resulting event, including retries, stale versions and uncertain native outcomes.

The current six-context design can represent the worked application without a shared database, cross-service foreign keys or a distributed write transaction. The console remains a seventh deployable for presentation and composition. The review found that the domain table needed explicit logical dataset, observed workload, managed workload-binding and reservation-journal distinctions. Those clarifications are now in the domain model. The binding and reservation behavior already required by the service specifications is made visible in the product vocabulary; no service or aggregate implementation has been added.

The recommended first-slice cardinalities remain one workload owner, one deployment per application/environment pair, and one WSD/domain pair per ordinary workload placement. These rules are sufficiently concrete for owner review but do not pre-approve schemas. The ADR disposition and delivery register remain the authorities for acceptance and progress.

## Record, field and execution authorities

The following is the recommended authority schedule for schema review. “Owner” identifies the single record writer; it does not claim a named person has approved the assignment. Actor/grant, tenant, native scope and concurrency are independently checked.

| Record or field group | Writer and source of truth | References and limits |
| --- | --- | --- |
| Tenant, membership, grant, approval, revocation | Governance | Authenticated effective actor/service and versioned policy; approval binds exact Planning plan bytes/digest. Other services cannot overwrite decisions. |
| Application, workload, environment, WSD, logical domain, dataset requirements, deployment revision | Catalogue | Same-tenant references and local invariants; complete revision snapshot includes resolved default/profile references. Actor and audit fields are server-derived. |
| Observed workload/volume/network/domain, endpoint incarnation and collection completeness | Inventory | Exact native identity and immutable observation generation; missing visibility remains unknown. Observation is not ownership or capacity reservation. |
| Assessment, requirement-fit findings, immutable Plan and compilation inputs | Planning | Pins Catalogue intent and Inventory/Assurance inputs. Current validity is separate from immutable plan bytes. No native writes or reservations. |
| Admission receipt, job dispatch, native-operation intent/attempt, field-owner schedule, managed bindings and reservation journal | Lifecycle | Local transaction and stable workflow/operation identities. Authenticated external receipts/readback establish what actually happened; a journal assertion alone does not. |
| Workflow history, timers and replay position | Lifecycle-owned Temporal workflows | Job/API status is a projection. Neither the console nor a second database state machine resumes native work independently. |
| Native resource existence/configuration and task state | Installed platform/service owner | Inventory and scoped Lifecycle observers retain observations with provenance. Saved Terraform state is not a substitute for current native facts. |
| Terraform-managed infrastructure fields | Explicit selected controller/state scope under Lifecycle authority | Record endpoint/incarnation, resource and sensitive subresource, state/backend scope, approved artifact and fencing epoch. No competing aggregate/per-route or network/guest writer. |
| Guest settings and externally owned IPAM, DNS, backup or identity fields | Designated guest controller or external service owner | Lifecycle obtains scoped receipts and observes postconditions; it does not infer ownership from a common workflow. Overlapping field control requires explicit transfer. |
| Evidence metadata/finalization, qualification and acceptance decision | Assurance | Producers submit scoped observations; independently authorized reviewers determine supported claims. Storage bytes/digests and custody must agree. |
| Session, presentation preferences and composed page state | Console | Scoped service APIs only; no service model/table access. Displayed approval or job state cannot grant authority. |

Managed workload bindings must distinguish `workload_id`, `deployment_id`, endpoint identity, native resource ID, incarnation, observed generation, source/target/retained role, approved field scope and owner epoch. These are proposed semantic requirements, not a locked wire schema. Binding two incarnations to a workload during migration is allowed; enabling two production writers for its consistency group is not.

## Commands, events and concurrency review

All command rows require verified service identity/audience and effective actor or explicitly bounded worker identity. Path/body tenant IDs are selectors, never proof. Owner-local authorization runs again before returning an accepted retry receipt. The common idempotency scope is tenant + effective principal + command + relevant parent; a different canonical payload under the same key conflicts. No command can write another service's private tables.

| Command or exchange | Writer and authority | Concurrency / event consequence |
| --- | --- | --- |
| Create application/initial intent | Catalogue; authorized application author with same-tenant environment/WSD/domain scope | One local transaction establishes application/deployment/revision, audit, receipt and outbox. `catalogue.application.created` / `catalogue.intent-revision.created` are Catalogue facts. |
| Append intent revision — example 1 | Catalogue; author authorized for parent application and selected deployment | Strong parent application ETag and parent revision; accepted retry before stale-ETag rejection, then local atomic revision/pointer/receipt/outbox. Event aggregate version is the application version. |
| Amend or retire reference definition | Catalogue; separate reference-administration authority | Expected reference revision plus transactional reference-use/retirement checks. Retained historical intents do not get rewritten. Producer owns reference-change/retirement events. |
| Register endpoint / request discovery | Inventory; approved endpoint administrator/collector scope | Expected endpoint revision for edits; collection key binds endpoint, scope and profile. Submission checks enrolled collector and generation; no native-write credentials. Inventory publishes only its task/generation facts. |
| Assess / compile — examples 2–3 | Planning; caller authorized for both application and candidate destinations | Persist selected input versions once; same key cannot silently refresh them. New assessment/plan has a new identity. Immutable output and separate validity view; Planning publishes completion/plan facts. |
| Approve / revoke — example 3 | Governance; independently permitted approver or revoker with exact plan/action/resource scope | Append decisions, bind plan digest/mode/conditions/expiry and policy revision, serialize local effective-history updates. Approval/revocation events notify, never replace current checks. |
| Admit job — example 4 | Lifecycle; execution scope and current Governance/Assurance/site/reservation checks | Atomically record admission/job/receipt/outbox, use stable Temporal workflow identity. Same accepted key yields same job; different key cannot bypass a resource hold. Lifecycle publishes admission fact. |
| Reserve / renew / confirm / release | Lifecycle journal; external owner performs its authorized allocation operation | Bind stable operation, demand/envelope digest and owner generation. Record partial/unknown results durably; safe release needs owner/native evidence. No event makes an external allocation transactional with the journal. |
| Perform native operation | Lifecycle; bounded worker grant, current owner epoch and approved effect scope | Journal before dispatch, retain request/attempt IDs; reacquire authority and resolve ambiguity before another attempt. Lifecycle owns outcome event after verified journal transition. |
| Cancel / reconcile / recover — example 5 | Lifecycle; requester authorized for job and selected recovery scope | Compare operation version, record request separately from outcome. Cancellation is not reversal; reconciliation is bounded observation, recovery may require a new plan/approval. |
| Finalize evidence / publish qualification | Assurance; scoped producer for upload, independent reviewer for qualification | Staged bytes and database reconcile; verify digest before finalization. Retry binds same object/metadata; corrections and revocations append records. Assurance owns evidence/support events. |
| Consume event — example 6 | Receiving context; authenticated producer plus subscribed tenant/service scope | Inbox event-ID and local projection update commit together. Track source aggregate version, reject rollback on old version and recover gaps through source API/replay. No native dispatch follows directly from an event. |
| Stale edit / authority unavailable — example 7 | Owning API independently evaluates resource/policy | `412` preserves the client's edits; mandatory authority unavailable means no new accepted command (`503`). Lost-response uncertainty uses original key/status, never an invented replacement. |

All seven example sections have a record writer and concurrency disposition. The apparent cross-service cycle “Planning uses Governance; Governance reads a Planning plan; Lifecycle reads both” requires no distributed transaction: first create and commit an immutable plan, later approve that exact record, then admit execution. Authorization may consult a read-only policy API; it must not recursively request plan creation or approval. Unavailable dependencies fail/hold their new command without holding a remote service's database transaction open.

Each service's outbox publishes only committed owned facts. Console publishes no authoritative domain events. Contract review must inventory consumer identities and independently authorize refresh APIs; a tenant field in an authenticated event is not unrestricted read authority. Events containing a historical actor preserve attribution even after actor revocation, while consumers execute any new privileged command only with current authority.

## Recommended decisions for accountable review

These are specific answers supported by the analysis, not already accepted owner decisions. The named ADR remains the disposition authority. Rejecting a recommendation must record its replacement and update affected examples before schema lock.

| Decision | Recommended answer and rationale | Review boundary / implementation consequence |
| --- | --- | --- |
| ADR-004 contexts | Keep Governance, Catalogue, Inventory, Planning, Lifecycle and Assurance as the six business contexts, with Console composition | Architecture and context owners ratify the authority schedule at G00.02. No shared Eloquent model or Python business package crosses the boundary. |
| ADR-013 deployment key | One active deployment identity per application/environment initially; stable workloads can appear in several environment revisions | Product/architecture review the first use cases at G00.02. Regions/sites belong to placement scope until a separate concurrent deployment dimension is explicitly needed. |
| ADR-013 WSD/domain sharing | Permit explicitly authorized same-tenant reuse, with separate lifecycle owner and retained consumers; exclude shared cross-tenant routing domains from ordinary profile | Security/context owners review at G00.02. Shared services use contracts/attachments. This preserves both multi-WSD application modeling and tenant isolation. |
| ADR-013 workload cardinality | Exactly one owning application and one WSD/domain pair in each ordinary placement; require separately designed cross-domain appliance support | Resolve at G00.02 before P03.01. Multihoming cannot become an implicit security exception. |
| ADR-013 revision/default rules | Immutable complete deployment snapshots; resolve/pin defaults on publication; initial application ETag serializes all deployment streams | Resolve at G00.02. This matches current examples and prevents cross-stream lost updates; assess finer-grained ETags only with a documented later concurrency change. |
| ADR-013 adoption and deletion | Distinguish logical, observed and managed identities; adopt by exact incarnation after reviewed no-change/ownership checks; retire references before disposal | Resolve baseline at G00.02; P09 details adoption and P07/P10 retention behavior. No cascade may release shared native resources or required evidence. |
| ADR-012 envelope/idempotency | Keep producer-owned versioned schemas, scoped idempotency, per-aggregate versions, outbox/inbox and explicit refresh on gaps | Ratify semantic baseline at G00.02. P00.03/P01.03 select exact schema tooling and prove PHP/Python canonicalization/golden vectors; those technical details are not inferred here. |
| ADR-009 revocation race | New privileged effects require current policy within an explicitly bounded freshness window; already dispatched effects remain held/observable until reconciled | IAM/security choose the actual window and failure policy in P00.03/P00.05. A notification-only revocation design is insufficient. No timing value is invented by this review. |
