## Native feasibility work once inputs exist

The preferred method remains `application_rebuild_restore`. The [initial-route procedure](../qualification/feasibility/initial-route.md) and RF01–RF11 in the [route review](p00-route-and-operations-review.md) already specify the observations; all remain unrun until actual evidence is recorded.

1. Reconcile the complete component/state/writer manifest (RF01), then build a clean quarantined target from pinned artifacts (RF02). Missing state or an unreproducible dependency is an explicit method limitation.
2. Prove application-consistent database and attachment capture/restore with exact integrity, relationship and metadata checks (RF03). Retain interrupted/corrupt/incomplete restore and lost acknowledgement outcomes (RF04–RF05).
3. Establish required and denied traffic, suppressed business effects and effective writer exclusion (RF06–RF07). Do not activate because a VM boots or a firewall object exists.
4. Demonstrate safe source return before target business writes (RF08) and separately preserve a known accepted target write through the selected recovery (RF09). A retained source that lacks that write is not valid post-write recovery.
5. Exercise stale control-plane authority and reconcile actual writers after restore (RF10). Measure the application outage, bounded resources and authorized cleanup/retention outcome (RF11).

Select the bounded P00 experiment scope with the qualification/platform roles and record exact case coverage. RF01–RF03 alone can inform method feasibility, but cannot satisfy G00.04's explicit requirement for both recovery boundaries. Full production qualification remains the later Q07/G08 obligation; neither this feasibility packet nor passing compatibility tools supplies native admission authority.
