# G00 — Product and architecture baseline review

Review P00 against G00.01–G00.06 in the [gate specification](../../implementation/gates.md), using the [P00 work packages](../../implementation/phases/p00.md). The product/architecture leads coordinate review; each criterion retains its defined accountable reviewer. This review establishes the bounded design and delivery baseline, including actual compatibility and feasibility observations.

## Assemble the review

1. Pin the product scope, application journey, domain model, service boundaries and requirements revision.
2. Gather owner assignments, now-blocking ADR decisions, compatibility locks/logs, [route feasibility findings](../feasibility/initial-route.md), approved operating measures and the executable P01 backlog.
3. Confirm E0 design review material is distinguishable from E1/E2 executed spike results; record unavailable environments and unresolved inputs explicitly.

## Criterion examination

| Criterion | Review action |
| --- | --- |
| G00.01 | Walk the first application journey with product and application owners; reconcile roles, exclusions and accountable assignments to each decision point. |
| G00.02 | Trace valid and invalid tenant/WSD/domain/instance examples; confirm one writer for intent, observation, plan, approval, allocation journal and effect. |
| G00.03 | Inspect exact locks/artifact identities and actual frontend/PHP/Python spike logs; reject unsupported combinations and confirm now-blocking ADRs are decided. |
| G00.04 | Reconcile the selected source/target/method/guest/data tuple with bounded experiments; challenge reproducible deployment, consistent capture/restore, complete datasets/configuration, fencing and both recovery boundaries for the preferred rebuild/restore method. Whole-VM conversion requires separate disk/boot/driver qualification. |
| G00.05 | Verify every load/outage/data/custody/retention target has units, scope, measurement and owner; review failed-dependency and post-write recovery cases. |
| G00.06 | Trace all 36 requirements to packages/gates/campaigns; check P01 outputs, owners, estimates and unblock conditions and deferred-decision checkpoints. |

## Resolve the review

Accept a criterion only when its required evidence and review exist. A written feasibility procedure cannot substitute for the bounded results required by G00.04; a dependency declaration cannot substitute for actual G00.03 execution.

For each unresolved item, identify the blocked criterion/package, responsible role, exact missing input/experiment and next action. Do not demand that every later ADR be closed in P00; confirm the decision register identifies its actual blocking checkpoint.

Record the immutable baseline review with criterion assessments, evidence IDs, source revisions, accepted scope, actual reviewer/date and blockers. Update only the [delivery register](../../implementation/delivery-register.yaml) for gate status. Passing G00 does not establish native qualification or authorize native execution.

## Reopen when

Review affected criteria again when product scope, context authority, stack selection, first migration method, operating targets or critical delivery dependencies change. Preserve the earlier decision and explain which baseline replaced it.
